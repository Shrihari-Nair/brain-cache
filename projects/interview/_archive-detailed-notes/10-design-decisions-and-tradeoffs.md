### Plain-words prerequisites
| Term | Meaning |
|---|---|
| **Trade-off** | getting one good thing by giving up another; a decision is only "good" relative to what was given up. |
| **Coupling** | how much one part breaks when another changes. Tight = breaks easily. |
| **Contract** | the unwritten or written agreement between two parts (here: Redis key names and JSON shapes). |
| **Durable** | data survives crashes and restarts. |
| **Structured output** | asking the LLM for machine-readable data (JSON) rather than prose. |
| **Evidence levels** | *Stated* = the repo says it; *Inferred* = I reasoned it; *Not recorded* = nobody wrote it down. |

**Evidence caveat about commits.** Several big commits have messages that do not describe their contents: `aa3e481` ("eval-harness-added") also adds the Piston executor, code judge, coding editor and Langfuse/Piston compose services; `f2243ad` (message about eval personas) also creates `agent/code_review_flow.py` and the shared `follow_up_policy_note`; `568bffc` (message about tests) also adds the follow-up hook, `llm_retry.py`, the report status machine and CI. ## 10.2 Mini write-ups (13 decisions)

### D1 — Redis as the contract between two services
- **Context.** Two processes with different lifecycles: a request/response API and a long-lived LiveKit worker running one process per interview.
- **Options.** (a) agent calls backend HTTP for plan/state; (b) backend pushes the plan to the agent via dispatch metadata; (c) shared store. **Chosen:** (c). The job metadata carries only `{"session_id": …}` (the `RoomAgentDispatch` metadata in `session.py`).
- **Consequences.** Independent restarts; no schema/migration tooling; but the "API" is key names + Pydantic shapes. Keys: `interview_plan:`, `session_state:`, `interview_report:`, `interview_report_status:`, `candidate_memory:` (exercise 1.2). A rename silently breaks across processes; tests guard the backend side only. Redis is unauthenticated and snapshot-only in compose (07 C4).
- **Evidence.** Spec L33; compose from `06219e4`; `agent/session_state.py` and `backend/main.py` from `74a0b97`; README L81 ("never call each other directly"). Why Redis rather than a DB: **rationale not recorded** beyond "state shared between FastAPI and agent".
- **Interview line.** "Redis is our integration bus; in production I would move durable data to a DB and keep Redis for ephemeral state."

### D2 — The agent imports the backend package
- **Context.** `InterviewPlan` and `report_pipeline` are needed on both sides.
- **Options.** duplicate, shared package, import across directories. **Chosen:** `sys.path.insert(0, <mockmind/>)` then `from backend…` (first in `7c62cfb`; the `sys.path.insert` line near the top of `agent.py`).
- **Consequences.** No drift between writer and reader schemas; the agent image must contain backend code (`agent/requirements.txt` lists backend dependencies; the Dockerfile `COPY . .`); the report pipeline runs inside the agent process using the agent's Redis settings.
- **Evidence.** `7c62cfb`, `agent/requirements.txt` comment "agent imports from backend package". **Rationale not recorded** beyond that comment.

### D3 — Agent dispatch inside the token
- **Context.** The agent must join only interview rooms, with the session id.
- **Options.** (a) auto-dispatch to every room; (b) server calls `agent_dispatch.create_dispatch` (what the spec shows); (c) token carries `RoomConfiguration(agents=[RoomAgentDispatch(...)])`. **Chosen:** (c) with `agent_name="mockmind-interviewer"` and metadata `{"session_id": …}`.
- **Consequences.** One HTTP call from the browser starts everything and the token endpoint makes no LiveKit API call (I minted one offline: exercise 2.5). The agent only joins rooms that request it by name. A wrong agent name or missing worker simply yields no agent; the UI only shows a timeout overlay after 25 s.
- **Evidence.** `74a0b97` `session.py` already used `RoomAgentDispatch`; spec L810–820 used `create_dispatch`. The change from spec to code has **no recorded rationale**.

### D4 — Plan first, then a constrained live interviewer
- **Context.** Live LLM calls are slow and the interview should feel structured.
- **Options.** One big live prompt; plan then live (chosen); fully scripted.
- **Consequences.** Live prompt contains the whole plan, answer key included (07 C8); system prompt is 17–29 k chars on synthetic plans and resent each call (08 §8.7). The plan can expire at 4 h. Flow control stays in code (`move_to_next_question`, counters).
- **Evidence.** Spec §1 and §7; `74a0b97` (resume/JD/question agents, `prepare.py`). Cost/latency motivation **not recorded**; the latency argument is **[Inference]**.

### D5 — Follow-up cap: code counts, model obeys
- **Context.** The prompt said "never more than 2 follow-ups" but nothing counted; `increment_follow_up_count()` existed unused (REPORT.md "earlier code audit" bullet).
- **Options.** Prompt only; count + inject note (chosen); auto-advance in code; validator before TTS.
- **Consequences.** The model sees `Follow-ups used: n/2` each turn (reproduced: exercise 1.4; at turn 4 the note even says `3/2`). Not a guarantee. The hook modifies the chat context, so speculative replies are discarded (02c §2c.7); cost **[Not measured]**. Coding questions skip the note.
- **Evidence.** Hook first appears in `568bffc` (`interviewer.py`, `test_follow_up_cap.py`) although its message never mentions it; shared `follow_up_policy_note` in `f2243ad`; motivation in `evals/REPORT.md`; A/B result inconclusive (07 B4).
- **Interview line.** "Prompts are requests; code is enforcement, and here we enforce the *counting*, not the behaviour."

### D6 — Thinking budget chosen per call site
- **Context.** Gemini 2.5 spends hidden "thinking" tokens from the output budget.
- **Options.** default (dynamic), off (0), fixed, `-1` dynamic explicitly. **Chosen:** 0 for analyzers (present in the first commit `74a0b97`), report 0 with a 16 384 ceiling (`7e98c15`), `-1` only when coding slots are requested (`3d57ab0`). The **live** agent LLM sets nothing (default behaviour) **[Library source]**.
- **Consequences.** Fewer truncated JSONs and faster extraction; coding-slot tag compliance improved from "about 1 in 4 slots dropped" to "13/13" per the commit message (07 A2 notes the code comment says 6 trials; not reproducible without live API). Live-turn latency effect of default thinking is **[Not measured]**.
- **Evidence.** `3d57ab0` body; comment `question_generator.py` L324–330; 07 A2/A3.

### D7 — LLM returns JSON text, parsed and validated, then retried
- **Context.** Every LLM output feeds typed code or the UI.
- **Options.** native `response_schema` (what the spec said it would use); `response_mime_type=application/json` + manual parse + Pydantic (chosen); function calling.
- **Consequences.** Works with free-form prompts; five copies of `_clean_json` (07 C11); `validate_report` accepts scores like 99 and a string `question_feedback` (exercise 2.1); a retry is a full paid call. Retry wrapper arrived in `568bffc`.
- **Evidence.** Spec L366 vs `74a0b97` code. **Rationale for abandoning `response_schema` not recorded.**

### D8 — Report generated inside the agent, with a status machine
- **Context.** The agent holds the transcript when the session ends.
- **Options.** agent generates (chosen; present since `74a0b97`, spec L1205); backend worker after webhook; client-triggered.
- **Consequences.** No extra transport; but generation happens in shutdown, where the worker's `shutdown_process_timeout` (10 s) applies, and `end_interview` fires an unreferenced task (07 D1). The status key (`pending/ready/failed`, `568bffc`) lets the UI show a retry button, but `pending` can be stranded (exercise 2.7 shows the state is never moved on).
- **Evidence.** `568bffc` message mentions "report pipeline and endpoints, … status handling". Why not a backend worker: **not recorded**. Live success rate **[Not measured]**.

### D9 — SSE for preparation progress
- **Context.** Three sequential LLM calls take long enough that silence feels broken.
- **Options.** polling with job id; WebSocket; SSE over POST (chosen, frontend reads the stream with `ReadableStream`, spec L1996).
- **Consequences.** Progress events with percent (5, 15, 20, 45, 50, 65, 70, 90, 100; exercise 2.6); one-way; a dropped stream loses the result (07 D6) although the plan may already be in Redis. Server errors become a generic message.
- **Evidence.** Spec L635, `74a0b97` `prepare.py`. Alternatives not discussed in the repo.

### D10 — Redis with TTLs instead of a database
- **Context.** Interview data is short-lived; no accounts.
- **Options.** Postgres; Redis (chosen).
- **Consequences.** Zero schema work and automatic expiry (plan/session 4 h, report/status 24 h, memory 1 year). Durability is only RDB snapshots in the compose default (08 §8.0): writes since the last snapshot can be lost and the anonymous volume may vanish on `down -v`. Nothing warns the user when a plan expires.
- **Evidence.** TTL `14400` in spec code and in `prepare.py`; `memory_store.py` L7 comment "a deliberate expiry, not forever". Why 4 h/24 h specifically: **not recorded**.

### D11 — Candidate memory: email-hash key, opt-in, outside the live prompt
- **Context.** Wanted cross-session personalization without accounts.
- **Options.** accounts/auth; email lookup (chosen); nothing.
- **Consequences.** `candidate_memory:<sha256(lowercased email)>`, 1-year TTL, forget-me endpoint (`071cfa5`), opt-in checkbox. Anyone who knows an email can read/alter its memory; hashing hides the key but not guessable emails **[Inference]**. Notes are model-written from candidate-influenced text, re-injected into the *next* question-generation prompt, so `04da133` wraps them as untrusted data. No lock on the read-modify-write (07 C18).
- **Evidence.** `d5173be`, `04da133` (states "doesn't claim to block a sufficiently motivated injection"), README "explicit accepted tradeoff".

### D12 — Execute candidate code in Piston, then let the LLM judge with real results
- **Context.** Reviewing code by eyeballing invites hallucinated verdicts.
- **Options.** LLM-only; local `exec` (unsafe); hosted judge API; self-hosted Piston (chosen).
- **Consequences.** Test pass counts are facts and overwrite the model's numbers (`code_judge.py` L132–134). Cost: privileged container; sequential per-test calls; Piston outage looks like wrong code (08 §8.8); `review_code` not retried.
- **Evidence.** `aa3e481` (executor, judge, compose service); README L240–241 explains "built to run untrusted code" and the infinite-loop SIGKILL check.

### D13 — A custom eval harness over text-mode interviews
- **Context.** An earlier audit found no behaviour evaluation (REPORT.md).
- **Options.** manual testing; third-party eval tool; custom harness (chosen) reusing real backend functions and mirroring tools.
- **Consequences.** Found real issues (truncated report JSON, follow-up violations, silent turns). Limits: voice path untested, one fixture pair, judge not calibrated, tool mirror approximate (07 C25). Manual-only CI workflow (`f2243ad`).
- **Evidence.** `aa3e481`, `f2243ad`, `evals/REPORT.md`.

## 10.3 Decisions that look odd but have reasons in the repo
- **Thinking off for report, on for coding plans:** each backed by an observed failure (07 A2/A3).
- **Duplicated `_clean_json` and tool mirrors:** no recorded reason; likely incremental growth **[Inference]**; listed as debt (07 C11).
- **Hardcoded fixtures in evals:** keeps runs comparable, narrows coverage (07 C17).

## 10.4 Principles I can defend with evidence
1. Prompts are requests; code is enforcement (D5).
2. Fail visibly: status keys, error events (D8).
3. Measure before tuning: thinking and truncation fixes came from observation (D6).
4. Keep untrusted text away from instruction positions (D11).
5. Ground model judgements in tool output (D12).

## 10.5 What I would change first and why
Auth + ownership (security), then durable report storage and backend-side report generation (reliability), then derive scores in code (correctness), then voice-path metrics and request timeouts (so tuning is evidence-driven).
